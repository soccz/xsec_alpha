# 운영 마무리와 성적표 전환 기준

2026-09-30. 목표는 기능 개수가 아니라 첫 실제 추천의 증거가 끝까지 이어지는 것이다.
모델·피처·IC 임계값·등록된 두 실험·Telegram 필수 보고는 변경하지 않는다.
현재 SHORT FREEZE는 유지한다. 원본 성적표가 추가됐다는 사실만으로 동결을 풀지 않는다.

## 첫 실제 회차

별도 호가·펀딩 규약의 첫 신호인 **2026-09-30 20:00 KST**를 고정한다. 이후 성공한
회차를 첫 회차 대신 선택하지 않는다. `forecast_audit.summary.lifecycle`과 감독 상태의
`operating_acceptance`에서 다음 경로를 자동 확인한다.

1. 당시 원본 점수와 Telegram API 수신 확인이 같은 해시로 연결되는가.
2. 선정 재현과 진입 전 후보 고정이 확인되는가.
3. 진입·종료 호가, 전체 원본 종목의 원시 가격 채점, 금액별 잔량 계산이 유효한가.
4. 공개 확정 펀딩 이력이 있는가. 정산 경계의 불확실성은 성공으로 숨기지 않는다.
5. 같은 첫 회차 증거 해시를 포함하는 원장 사본이 실제로 복원·재검사됐는가.
6. 공개 페이지에서 종결 기록 해시와 그 게시물의 암호화 summary 파일 해시가 일치하는가.

각 단계는 대기·확인·누락/실패/불확실로 구분한다. 등록 기한을 넘긴 미해결 단계는
실패로 종료한다. 모든 단계가 끝났어도 공백이 있으면 `closed_with_gaps`이며 수익성이나
완전한 운영 성공으로 부르지 않는다. 정상 자료도 펀딩 조회까지 시간이 필요하므로
첫 추천 도착만으로 전체 완료가 되지 않는다.

`output/operating_acceptance/closed.json`은 최초 종결 기록과 복원 checkpoint를 봉인한다.
새 회차나 늦게 복구한 자료로 덮어쓰지 않는다. 공개 반영 검증은 별도
`publication.json`에 저장하고, 실패한 조회도 `publication_attempts/`에 남긴다.
종결 기록과 성공한 게시 수신증은 `output/operating_acceptance_backup/`에도 검증 사본을
남긴다. 한쪽이 사라지면 같은 기록을 복구하지만 손상·서로 다른 기록은 덮어쓰지 않고
오류로 처리한다. 동일 디스크 사본이므로 물리 디스크 고장은 보호하지 않는다.
공개 JSON에는 종결 해시와 암호화 파일 해시만 추가한다. 상세 증거는 암호화 영역에 둔다.
실제 사람의 Telegram 열람, 브라우저 동작 전체, 실제 체결·계좌 현금흐름의 증거는 아니다.
공개 반영이 종결 후 30분 이상 미확인되면 별도 운영 점검에서 표시한다.

## 수집 시간과 중단

- 감독 작업에서 예측 감사가 다른 실험 재평가보다 먼저 실행된다.
- 감사 안에서도 원본·전송 연결과 호가 수집을 과거 가격 평가·IC 대조보다 먼저 실행한다.
- 각 호가·펀딩 관찰은 개별 commit한다. 이후 분석 오류나 프로세스 중단이 이미 확정한
  관찰을 취소하지 않는다. 재시작은 저장된 키를 건너뛰며 실패를 좋은 가격으로 바꾸지 않는다.
- HTTP 응답 수신과 로컬 commit 사이의 전원 상실까지 정확히 한 번 수신을 보증하는 것은 아니다.
  원격 API와 SQLite 사이에 분산 트랜잭션은 없다.
- 펀딩 적체는 모든 현재 호가 수집 뒤에 처리한다. 기존 90초 수집 예산·첫 관찰 정책은 유지한다.
- 감사의 수집 단계·평가 단계·전체 시간·원장 행 수를 기록한다. 수집 60초 또는 감사 전체
  120초 초과는 여유 시간 경고다. 기존 5분 관찰 창이나 서비스 180초 제한을 늘린 것이 아니다.
- 보고서 해시는 검증 회차마다 모든 보고서를 다시 해싱하지 않고 한 번 색인한다.
  해시 검증·선정 재현·호가 산술·원장 무결성 검사는 생략하지 않는다.

격리 검증:

```bash
python -m pytest tests/test_execution_audit.py tests/test_operating_acceptance.py tests/test_ops_status.py -q
python scripts/verify_audit_load.py --windows 336
```

부하 도구는 별도 임시 원장에 336회, 회차당 100종목, 후보 합집합 10개, 50단계 호가를
생성한다. 감사·복원 시간을 기록한 뒤 임시 원장을 정리한다. 결과는
`output/operating_checks/load-336.json`에 남고 운영·실험 원장으로 편입되지 않는다.
실제 HTTP 지연·시장 상황과 전체 감독 작업의 다른 실험·Git 게시 비용은 이 수치에 포함되지
않는다. 서비스 실제 실행도 별도로 확인하며 이 측정으로 무제한 장기 운영을 보증하지 않는다.

9월 30일 실측: 같은 336회 규모에서 수정 전 감사 326.770초·복원 217.585초,
합계 544.354초로 180초 한도를 초과했다. 보고서 해시 색인 후 176.736초였으며,
중복 재검사를 정리한 최종 버전은 **감사 83.662초·복원 37.740초, 합계 121.402초**,
수집 단계 45.028초였다. 원장은 12,775행이며 생성한 336회 뒤의 미수집 예정 2회도
숨기지 않고 누락으로 처리한다. 최종 기록은 `load-336.json`, 중간 색인 버전 기록은
`load-336-index-only.json`이다. 동시 테스트·머신 부하에 따라 소요 시간은 달라질 수 있다.

완전한 산술 재현은 감사 시작·종료와 백업 snapshot에서 유지한다. 임시 복원본은 이미
재현 검사를 통과한 snapshot과 파일 SHA-256이 같은지, SQLite 무결성과 행 수가 같은지
확인한다. 같은 바이트의 산술을 다시 계산하던 중복만 줄인 것이며 원본 검증을 건너뛰지 않는다.
격리된 사용자 systemd 작업에서 `os._exit(42)`로 중간 프로세스를 종료한 뒤 재개하는
테스트도 성공했다. 실제 서버 재부팅이나 거래소 장애 전체를 재현했다는 뜻은 아니다.

## IC 기준 전환

**현재 운영 출처는 `output/ic_history.json`의 기존 재계산 IC다. 이번 작업은 전환하지 않는다.**
별도 `gate_shadow`는 같은 최근 만기 세 회차에 기존 임계값을 적용해 판단을 비교한다.
원본 점수 누락, 회차 공백, 모델 버전 혼합이면 원본 쪽은 판단 불가다. 좋은 회차만 모으거나
이전 모델의 성적을 신모델에 이어 붙이지 않는다. 비교한 기존 IC도 같은 세 회차에 제한하므로
실제 게이트가 지금 읽은 이력의 시점과 다를 수 있다. LONG은 대상이 아니며 기존 정책을 유지한다.

전환 검토의 순서는 다음으로 고정한다.

1. 첫 실제 회차가 공백 없이 종결되고, 복원 및 공개 반영이 확인돼야 한다.
2. 등록된 첫 신호부터 **28개 예정 회차**의 원본·결측·대조 결과를 검토한다. 28개는
   7일 운영 범위를 점검하는 최소 기준이지 통계적 유의성·투자 우위 기준이 아니다.
   실패를 뒤의 성공 회차로 대체하지 않는다. 모델 버전별로 분리하며 불일치·누락이 있으면
   원인을 기록하고 수정 검토를 먼저 한다. 비교 차이를 0으로 만들 필요는 없다.
3. 새로운 운영 계약을 별도 승인한다. 원본 IC의 지연·누락 시 watch-only, 현재 모델 버전,
   평가 대상·시각, 세 회차 연속성, 적용 시작 회차를 명시한다. 기존 이력을 소급 덮어쓰지 않는다.
4. 전환 전후 코드·설정·모델 해시와 이전 계약을 보존하고, 같은 회차의 판단 차이를 검토한다.
   변경을 적용하는 별도 배포에서는 원본 누락·무결성 오류·지연을 정상으로 취급하지 않는지
   장애 테스트를 다시 실행한다. 기존 60회 실험과 336회 파일럿은 변경하지 않는다.
5. 전환 후 증거 손상·누락·새 모델의 표본 부족이 생기면 실행 가능한 신호를 먼저 막고
   필수 참고 코인 보고는 유지한다. 원인을 조사해 이전 승인 계약으로 복구할 수 있지만,
   예전 게이트가 더 낙관적이라는 이유만으로 자동 복구하거나 FREEZE를 해제하지 않는다.

자동 전환·새 모델 승격·투자금 증액은 없다. 검토 조건을 만족한 뒤의 전환 배포는 명시적인
다음 결정이며, 조건을 충족하기 전에 이번 마무리의 성과로 주장하지 않는다.
